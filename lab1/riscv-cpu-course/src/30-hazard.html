第 9 章 · 管線與 hazard

時空圖：一張圖看完整條管線

前面幾章都在跟著一道指令走。但管線的重點從來不是一道指令走得多快，而是五道指令同時在不同的級上工作。要討論這件事，需要一種新的圖：橫軸是時間（週期），縱軸是指令，每一格寫著「這道指令在這個週期位於哪一級」。這張圖叫時空圖 (pipeline diagram)，是這一篇後面所有討論的共同語言。

延遲與吞吐量是兩件事

從上圖讀兩個數字：

  • 延遲 (latency)：一道指令從進入管線到離開，永遠是 5 個週期。管線沒有讓任何一道指令變快，反而因為多了四排管線暫存器而讓單道指令變慢一點點。
  • 吞吐量 (throughput)：穩定之後每個週期完成一道指令。這才是管線買到的東西。

如果把同樣的五道指令交給一顆「單週期做完整道指令」的 CPU，它每道指令要花一個很長的週期；管線把那個長週期切成五段，讓時脈可以快五倍左右，代價是延遲變成 5 段。切得愈多段，時脈愈快，但只要有一道指令必須等另一道，浪費的就是「段數」那麼多個週期。這句話就是接下來三章的主題。

IPC：拿一個數字衡量它

衡量管線效率的標準指標是 IPC (instructions per cycle)：完成的指令數除以花掉的週期數。倒過來寫就是 CPI (cycles per instruction)。理想的五級管線 IPC = 1；實際上永遠小於 1。

lab1 的模擬器加上 +stats=1 就會印出這三個數字。把 riscv-add 這個測試跑在 riscvstall（也就是你現在手上這顆只會 stall、還不會 bypass 的處理器）上：

 ipc        = 0.495726

232 道指令花了 468 個週期。差不多一半的週期是浪費掉的。換成會隨機延遲記憶體回應的 -rand- 版本更慘：

那 236 個被浪費的週期去哪了？答案有三個：data hazard 造成的 stall（第 11 章）、control hazard 造成的 squash（第 12 章）、以及記憶體沒有馬上回應造成的 stall（第 13 章）。作業的 Objective 3（bypass，第 14 章起）就是要把第一種浪費拿回來大半——做完之後回來重跑這個數字，是這份作業最有成就感的一刻。

第 10 章 · 管線與 hazard

三個基本動作：bubble、stall、squash

管線只要遇到「這個週期不能照常往前走」，能做的事只有三種。這三種動作在 riscvstall-CoreCtrl.v 裡的實作非常固定，看懂一次，後面所有 hazard 處理都只是在決定「什麼時候做哪一個」。

動作做什麼誰受影響這顆 CPU 的訊號
bubble某一級裡面沒有真的指令，只是一個佔位的空洞一級bubble_Fhl…bubble_Whl
stall某一級原地不動（管線暫存器不載入新值），前面所有級跟著停這一級 + 它前面全部stall_Fhl…stall_Whl
squash已經抓進來的指令作廢，變成 bubble一級squash_Fhl、squash_Dhl

差別要記牢：stall 是「等一下」，指令還在，之後會繼續執行；squash 是「不要了」，那道指令永遠不會完成。bubble 則是前兩者的共同產物——stall 一級會往下游擠出 bubble，squash 一級會把自己變成 bubble。

bubble 位元與 inst_val

教科書上常說「插入 nop」，但這顆 CPU 沒有真的去合成一道 nop 指令。它每一級只多帶一個位元 bubble_Shl：1 代表「這一級裝的東西不是真的指令」。handout 3.5 對這個設計的說明是：

handout 3.5

Bubble bits indicate whether a pipeline stage contains an invalid entry. … This mechanism represents invalid entries without requiring explicit nop instructions. Control logic must prevent bubble entries from causing architectural side effects, such as register writes or memory requests.

每一級再把 bubble 位元和 squash 訊號合成一個「這一級現在是不是一道有效指令」的旗標：

riscvstall/riscvstall-CoreCtrl.v · 第 644 行（X 級；其他級形狀相同）
wire inst_val_Xhl = ( !bubble_Xhl && !squash_Xhl );
常見錯誤

「反正 bubble 的指令欄位是 x，算出來的東西也沒人用」——不對。dmemreq_val 如果漏掉 inst_val_Xhl，bubble 會對記憶體發出一個位址是 x 的 request，模擬直接爆掉；rf_wen_out_Whl 漏掉的話，bubble 會拿一個 x 值去寫某個暫存器。這類 bug 的症狀是「測試在某個看起來無關的地方開始噴 x」。

stall：兩件事一起做

stall 一級不是只有「不要載入」而已，而是兩個動作同時發生：

  1. 這一級的管線暫存器 enable 關掉，原封不動保留現在的內容（就是基礎篇第 15 章的 enable 暫存器，else if (!stall_Xhl)）。
  2. 往下游塞一個 bubble。因為下一級並沒有停，它這個週期一定要收到某個東西；既然上游卡住了，只能給它一個空洞。
riscvstall/riscvstall-CoreCtrl.v · 第 585–588 行
wire bubble_sel_Dhl  = ( squash_Dhl || stall_Dhl );
wire bubble_next_Dhl = ( !bubble_sel_Dhl ) ? bubble_Dhl
                     : ( bubble_sel_Dhl )  ? 1'b1
                     :                       1'bx;

stall 鏈：從最後一級往前傳

管線只能「往前面擠」：如果 M 卡住了，X 就不能把東西送進 M，於是 X 也得卡住，依此類推。所以每一級的 stall 訊號都是「我自己的 stall 原因 OR 後面那一級的 stall」，而 W 級永遠不 stall，整條鏈就從 0 開始往前長。

riscvstall/riscvstall-CoreCtrl.v · 第 196、579–581、682、742、803 行
assign stall_Whl = 1'b0;
assign stall_Mhl = stall_dmem_Mhl;
assign stall_Xhl = ( stall_Mhl || stall_muldiv_Xhl || stall_dmem_Xhl );
assign stall_Dhl = ( stall_Xhl || stall_muldiv_Dhl || stall_hazard_Dhl );
assign stall_Fhl = ( stall_Dhl || stall_imem_Fhl );

一格一格看：D 被 stall 三個週期時發生什麼事

squash：把已經抓進來的指令作廢

stall 的前提是「這道指令之後還要執行」。但分支跳走的時候，已經抓進 F 和 D 的指令根本不該存在——留著它只會算出錯的結果。這時要用的是 squash：把那一級直接標成 bubble。

riscvstall/riscvstall-CoreCtrl.v · 第 187–189、548 行
assign squash_Fhl
  = (inst_val_Dhl && brj_taken_Dhl)      // D 裡的 jal/jalr 要跳
 || (inst_val_Xhl && brj_taken_Xhl);     // X 裡的分支成立

wire squash_Dhl = ( inst_val_Xhl && brj_taken_Xhl );
squash 之後那一格還是 bubble

squash 不是另一套機制，它最後也是走 bubble 這條路：bubble_sel_Fhl = ( squash_Fhl || stall_Fhl || imem_abandoned_Fhl )（第 220 行）。也就是說，「作廢」和「等待」在硬體上共用同一顆 mux，差別只在誰把 select 拉起來。

想一想

如果某一級同時 stall 和 squash（例如 X 有分支成立、同時 D 有 data hazard），會怎樣？

看答案

bubble_sel_Dhl = squash_Dhl || stall_Dhl，兩者都會把 select 拉到 1，所以往下游送的一定是 bubble——結果一致。但要注意 D 自己的暫存器 enable 是 !stall_Dhl：stall 時 D 保留舊內容，被 squash 的那道指令其實還留在 D 裡，只是它的 bubble_Dhl… 沒有被更新。真正讓它作廢的是 inst_val_Dhl = !bubble_Dhl && !squash_Dhl 這個組合條件：只要 squash_Dhl 為 1，那一級這個週期的所有對外動作就都被關掉了。這就是為什麼 squash 要同時出現在 inst_val 和 bubble_sel 兩個地方。

第 11 章 · 管線與 hazard

Data hazard：讀到還沒寫回的值

第一種冒險 (hazard)。兩道指令排在一起：

示意範例
addi x1, x0, 5      # 寫 x1
add  x2, x1, x1     # 讀 x1

在單週期 CPU 上這完全沒問題：第一道做完才輪到第二道。但在管線上，第二道指令在 D 級讀暫存器檔的時候，第一道還在 X 級——它算出來的 5 還躺在 ALU 輸出上，離「寫進暫存器檔」還有三個週期。

暫存器檔沒有內部 bypass

有些設計會在暫存器檔裡做「同週期寫入直通讀出」。riscvstall-CoreDpathRegfile.v 沒有：讀出的永遠是 registers[raddr] 的現值。所以「生產者在 W、消費者在 D」的同一個週期仍然算是 hazard，這一點直接決定了下面 stall 幾個週期。

riscvstall 的作法：把消費者擋在 D

最笨但最正確的解法：既然 D 讀不到對的值，就讓它不要往前走，一直停在 D，直到生產者離開 W 為止。

真正的 stall_hazard_Dhl

這段程式碼是整個 riscvstall 最值得逐字讀的一段。它把 D 級的兩個來源暫存器編號，分別跟 X、M、W 三級的目的暫存器編號比對，六項任一成立就 stall：

riscvstall/riscvstall-CoreCtrl.v · 第 557–575 行
wire stall_hazard_Dhl   = inst_val_Dhl && (
                          ( rs1_en_Dhl && inst_val_Xhl && rf_wen_Xhl
                            && ( rs1_addr_Dhl == rf_waddr_Xhl )
                            && ( rf_waddr_Xhl != 5'd0 ) )
                       || ( rs1_en_Dhl && inst_val_Mhl && rf_wen_Mhl
                            && ( rs1_addr_Dhl == rf_waddr_Mhl )
                            && ( rf_waddr_Mhl != 5'd0 ) )
                       || ( rs1_en_Dhl && inst_val_Whl && rf_wen_Whl
                            && ( rs1_addr_Dhl == rf_waddr_Whl )
                            && ( rf_waddr_Whl != 5'd0 ) )
                       || ( rs2_en_Dhl && ... )      // rs2 對 X / M / W，共三項
                       ... );

四個守門條件，少一個就是一個 bug

條件它在擋什麼拿掉會發生什麼
rf_waddr_* != 5'd0x0任何寫 x0 的指令（例如編譯器常用 addi x0, x0, 0 當 nop）都會讓後面每一道讀 x0 的指令 stall 三次。x0 恆為 0，讀它永遠是對的，完全不需要等。
inst_val_*bubble 與被 squash 的指令bubble 的 rf_waddr 是上一道指令留下來的殘值（管線暫存器只在 !stall 時更新，bubble 不會把資料欄位清成 0）。拿殘值去比對，會莫名其妙 stall——甚至在剛 reset 完是 x，比較結果是 x，整條 stall 訊號變成 x。
rf_wen_*不寫暫存器的指令sw、bne 這類指令的 rf_waddr 欄位是無意義的（控制表裡通常填 rx）。不檢查 rf_wen 就會拿垃圾編號去比。
rs1_en_Dhl / rs2_en_Dhl指令根本沒用到的來源欄位見下。

最後一項跟你的作業直接相關。rs1_en／rs2_en 是第 5 章那張控制表裡的兩欄，意思是「這道指令的 ir[19:15]／ir[24:20] 這幾個位元真的是來源暫存器編號嗎」。以 I-type 的 addi 為例，ir[24:20] 其實是立即值的一部分，所以 rs2_en 必須是 n。

常見錯誤

你在控制表新增一列時把 rs2_en 填錯，症狀分兩種，而且都不會馬上炸：

填成 y（多讀了）：立即值的某幾個位元被當成暫存器編號去比對，結果偶爾會撞上前面指令的目的暫存器，多 stall 幾個週期。程式答案是對的，只是慢——riscvstall 階段你可能根本察覺不到，但到了 Objective 3 做 bypass，這個錯誤會讓你「把立即值位元對應的暫存器值 bypass 進來」，答案就真的錯了。

填成 n（漏讀了）：真正需要的相依被漏掉，add 拿到舊值，測試直接失敗。這種比較好抓，因為 tests/riscv/riscv-*.S 裡的 TEST_RR_* 巨集就是專門在測這個。

六項比對的全貌

1（緊接著）3X → M → W

為什麼測試檔裡有一堆 nop

tests/riscv/riscv-macros.h 定義了 TEST_INSERT_NOPS_0 到 TEST_INSERT_NOPS_10，測試巨集會在生產者和消費者之間插入 0～10 道 nop。這不是為了「避開 hazard」，剛好相反：它是為了系統性地掃過所有相依距離，確保距離 1、2、3 的每一條 bypass 路徑都被測到。第 16 章會再回來看這些巨集。

代價

回到 第 9 章的數字：riscv-add 的 232 道指令花了 468 個週期。這個測試幾乎每一組 TEST_RR_OP 都是「設好兩個來源、馬上做運算、馬上檢查結果」，相依距離大多是 1 或 2——每一組就這樣送掉兩三個週期。IPC 0.4957 幾乎全部是這裡吃掉的。

而這些 stall 完全是不必要的。第 1 週期 addi 算出的 5，在第 3 週期就已經躺在 X／M 之間的管線暫存器上了；add 需要的東西明明已經在晶片裡，只是沒有一條線把它送到該去的地方。補上那幾條線，就是 第 14 章開始的旁路／前饋 (bypass / forwarding)。

第 12 章 · 管線與 hazard

Control hazard：抓錯指令了

第二種 hazard 跟資料無關，跟下一道指令是哪一道有關。F 級每個週期都要送出一個位址去抓指令，但遇到分支時，「下一道指令的位址」要等到分支條件算出來才知道——而條件是在 X 級用 ALU 算的。F 不可能等三個週期，它只能猜。

這顆 CPU 的猜法是最簡單的一種：預測不跳 (predict not-taken)——先照 pc + 4 一直抓下去。猜對就零成本，猜錯就把抓錯的指令 squash 掉。

jal 就好一點：跳躍目標只需要 pc + 立即值，D 級解碼完就算得出來，不必等 ALU。

PC mux：四個輸入來自三個不同的級

「預測不跳」在電路上長什麼樣子？就是 PC 那顆 mux 的預設輸入是 pc+4，其他三個輸入是從後面的級倒著拉回來的修正值。

riscvstall/riscvstall-CoreDpath.v · 第 81–91 行
assign pc_plus4_Phl       = pc_plus4_Fhl;     // 來自 F
assign branch_targ_Phl    = branch_targ_Xhl;  // 來自 X
assign jump_targ_Phl      = jump_targ_Dhl;    // 來自 D
assign jumpreg_targ_Phl   = jumpreg_targ_Dhl; // 來自 D

assign pc_mux_out_Phl
  = ( pc_mux_sel_Phl == 2'd0 ) ? pc_plus4_Phl
  : ( pc_mux_sel_Phl == 2'd1 ) ? branch_targ_Phl
  : ( pc_mux_sel_Phl == 2'd2 ) ? jump_targ_Phl
  : ( pc_mux_sel_Phl == 2'd3 ) ? jumpreg_targ_Phl
  :                              32'bx;

誰說了算：X 的分支優先於 D 的跳躍

為什麼 X 要贏？想一個具體情境：

同一個道理解釋了 brj_taken_Dhl 為什麼長這樣：

riscvstall/riscvstall-CoreCtrl.v · 第 475 行
wire brj_taken_Dhl = ( inst_val_Dhl && !stall_Dhl && cs[`RISCV_INST_MSG_J_EN] );
  • inst_val_Dhl：D 裡如果是 bubble 或已被 squash，當然不能跳。
  • !stall_Dhl：這一項比較微妙。如果 D 被 stall 住，這道 jal 這個週期不會前進；但 brj_taken_Dhl 只要拉起來，PC 就被改掉、squash_Fhl 也會拉起來。下個週期 D 還是同一道 jal，它會再跳一次——而 PC 早就跳走了，於是第二次跳的起點是錯的。加上 !stall_Dhl，等於規定「只有在我這個週期真的要離開 D 的時候，才對外宣告我要跳」。
想一想

brj_taken_Xhl = inst_val_Xhl && any_br_taken_Xhl（第 666 行）。如果拿掉 inst_val_Xhl，一個停在 X 的 bubble 會發生什麼事？

看答案

bubble 的 br_sel_Xhl 是上一道指令留下來的殘值（管線暫存器只在 !stall_Xhl 時更新，bubble 位元和資料欄位是分開的）。如果上一道剛好是 bne，殘值就是 br_bne；而 ALU 的比較結果 branch_cond_ne_Xhl 是對當下輸入（也是殘值）算出來的，完全可能是 1。於是這個不存在的指令會跳走，並且順手 squash 掉 F 和 D 兩道真正該執行的指令。症狀是程式在某個分支附近隨機跳到奇怪的位址。
更麻煩的是 第 11 章提過的：剛 reset 完這些殘值是 x，比較結果是 x，pc_mux_sel_Phl 也變成 x，整顆 CPU 從第一個週期就死了。凡是「往回影響 PC 或機器狀態」的訊號，一律要先問 inst_val。

把兩種 hazard 的成本放在一起看

data hazard 一次最多吃掉 3 個週期，但它非常頻繁（幾乎每一對相鄰指令都可能撞上）；control hazard 一次只吃 1～2 個週期，但無法用 bypass 消除——Objective 3 做完之後，data hazard 的 stall 會掉到只剩 lw 之後緊接著用的那一種，而分支的 2 個週期仍然原封不動地在那裡。要再動它，就得做分支預測，那超出這份作業的範圍。

第 13 章 · 管線與 hazard

進階：val/rdy 記憶體與取指狀態機

這章可以先跳過

要完成 Objective 1～3，你其實不需要改這一章講的任何東西。但你非常容易不小心弄壞它：所有 -rand- 結尾的模擬器（記憶體回應會隨機延遲）都仰賴這裡的邏輯。如果你的 riscv-*-stall.out 全過、riscv-*-stall-rand.out 卻掛掉，答案九成在這一章。

前面所有時空圖都偷偷假設「指令記憶體一定在下一個週期把指令交出來」。真實的記憶體不保證這件事，所以 lab1 的兩個記憶體埠都用 val/rdy 交握（基礎篇第 14 章）：送方拉 val，收方拉 rdy，兩個都是 1 的那個時脈上升緣，一筆資料才算交出去。

取指狀態機

riscvstall/riscvstall-CoreCtrl.v · 第 119–135、147–150 行
localparam imem_idle = 1'b0;    // 沒有 request 在外面
localparam imem_wait = 1'b1;    // 有一筆 request 已送出、response 還沒回來

reg imem_state_Fhl;
always @ (posedge clk) begin
  if (reset)                          imem_state_Fhl <= imem_idle;
  else if (imem_send_accepted_Fhl)    imem_state_Fhl <= imem_wait;
  else if (imem_consumed_Fhl)         imem_state_Fhl <= imem_idle;
end

wire imem_send_accepted_Fhl = imemreq_val  && imemreq_rdy;    // req 交握成立
wire imem_consumed_Fhl      = imemresp_val && imemresp_rdy;   // resp 交握成立

另外三條線值得記住：

訊號行意思
imemreq_val = imemreq_pending_Fhl || imemreq_start_Fhl173val 一旦拉起來，就要一直維持到對方 rdy 為止——這是 val/rdy 的基本規矩，imemreq_pending_Fhl 就是那個「還沒被接走」的記憶位元（第 160–171 行）。
imemresp_rdy = !stall_Dhl226「我收得下嗎」＝「D 這拍會不會前進」。D 卡住時就不收，讓記憶體自己抱著。
stall_imem_Fhl = !imemresp_val194手上沒有一份可用的回應，F 就 stall。注意它沒有加任何條件——只要回應沒到，F 一律停。

麻煩的情況：request 還在飛，分支卻跳了

假設 F 在某個週期送出了對 pc+4 的 request，但記憶體慢了兩拍還沒回應。就在這期間，X 級的分支成立了——squash_Fhl 拉起來，PC 也改成了分支目標。問題有兩個：

  1. 那筆還在外面的 request 回來的時候，帶回的是錯路上的指令。不能讓它進 D。
  2. pc_mux_out_Phl 是組合算出來的，只在 brj_taken_Xhl 為 1 的那一個週期是正確的分支目標；下一個週期它就變回 pc+4 了。但 F 這時還 stall 著（在等回應），來不及把正確位址收進 pc_Fhl。

兩個問題各有一個記憶位元負責。第一個在控制器：

riscvstall/riscvstall-CoreCtrl.v · 第 202–221 行
reg imem_abandoned_Fhl;
always @ (posedge clk) begin
  if (reset)                        imem_abandoned_Fhl <= 1'b0;
  else if (imem_consumed_Fhl)       imem_abandoned_Fhl <= 1'b0;
  else if ( squash_Fhl
         && ( ( imem_state_Fhl == imem_wait )
           || imemreq_pending_Fhl
           || imem_send_accepted_Fhl ) ) imem_abandoned_Fhl <= 1'b1;
end

wire bubble_sel_Fhl  = ( squash_Fhl || stall_Fhl || imem_abandoned_Fhl );

第二個在資料路徑：

riscvstall/riscvstall-CoreDpath.v · 第 96–115 行
reg        pc_redirect_pending;
reg [31:0] pc_redirect_targ;

always @ (posedge clk) begin
  if (reset)            begin pc_redirect_pending <= 1'b0; ... end
  else if (!stall_Fhl)        pc_redirect_pending <= 1'b0;
  else if (squash_Fhl) begin
    pc_redirect_targ    <= pc_mux_out_Phl;   // 把正確目標存起來
    pc_redirect_pending <= 1'b1;
  end
end

wire [31:0] pc_mux_out_Phl_final
  = pc_redirect_pending ? pc_redirect_targ : pc_mux_out_Phl;

資料記憶體：request 在 X，response 在 M

dmem 的切法和 imem 一樣，只是跨的是 X 和 M：

riscvstall/riscvstall-CoreCtrl.v · 第 655、678、738、742、748 行
assign dmemreq_val   = ( inst_val_Xhl && !stall_Xhl && dmemreq_val_Xhl );
wire stall_dmem_Xhl  = ( dmemreq_val_Xhl && inst_val_Xhl && !dmemreq_rdy );

wire stall_dmem_Mhl  = ( !reset && dmemreq_val_Mhl && inst_val_Mhl && !dmemresp_val );
assign stall_Mhl     = stall_dmem_Mhl;
assign dmemresp_rdy  = !stall_Mhl;
lab 用的鐵則

你改管線時只要守住這三條，-rand- 測試就不會壞：

1. 每一筆回應剛好被消費一次。*resp_rdy 要和「這一拍那個級真的會前進」完全一致，不多不少。

2. 絕不從一個被 stall 住或裝著 bubble 的級發出 request。這就是 dmemreq_val 上那兩個守門條件 inst_val_Xhl && !stall_Xhl 的意義。

3. val 拉起來之後不能中途放掉，要一直等到對方的 rdy 出現（imemreq_pending_Fhl 就是為此存在）。

想一想

你在 Objective 4 把管線加長兩級之後，dmemresp_rdy = !stall_Mhl 這條線需要改嗎？

看答案

要看你把 dmem 的回應接在哪一級。這條線的意思永遠是「接收這筆回應的那一級這一拍會不會前進」。只要你沒有把 M 級搬走，它就不用改；但如果你為了配合乘除法器把 W 之前多插了兩級，而讓資料回寫改在更後面才用到，就要重新問一次：這筆回應是被誰收下的？那一級的 stall 是什麼？永遠不要憑感覺改這條線，要從「誰消費它」推回來。
