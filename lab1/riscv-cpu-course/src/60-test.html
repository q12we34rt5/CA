第 20 章 · 測試與除錯

從一個 .S 檔到 *** PASSED ***

前面十九章都在講電路。可是你在終端機看到的只有一行 *** PASSED *** 或 *** FAILED *** (status = 137)。這一章把中間那條長長的管線拆開：一個組合語言檔怎麼變成 .vmh、.vmh 怎麼進到記憶體、CPU 怎麼「回報」成績，以及 status = 137 的 137 到底是什麼。看懂這條路，除錯就從「亂猜」變成「查表」。

測試框架本身的 Verilog 語法（$display、initial、plusargs）在基礎篇第 16 章講過，這裡不重複，只講 lab1 特有的部分。

整條工具鏈

右半邊（.vmh 之後）由 build/ 的模擬器負責，左半邊由編譯器負責。在目前的 lab1 裡，build/Makefile 自己就有 %.elf → %.dump → %.vmh 三條規則，所以在 build/ 下 make 一次就會把 tests 清單裡的測試從 .S 一路做到 .vmh；講義 4.1 節那套 tests/build/ + ../configure + ../convert 的流程做的是同一件事，只是產物落在 tests/build/vmh/。兩邊都可以，build/Makefile 的 VPATH 兩個目錄都會找。

    riscv32-unknown-elf-objdump -EL -sz --section=.xcpthandler --section=.text --section=.data $x > $x.dump

一個測試檔長什麼樣子

每個 tests/riscv/riscv-*.S 的骨架都一樣：TEST_RISCV_BEGIN 開頭、一長串檢查、TEST_RISCV_END 結尾。檢查與檢查之間沒有 if/else，只有一條「直線」：每個檢查都用一個 bne 判斷「算錯了就跳去 _fail」，算對就自然往下走到下一個檢查。全部走完才會掉進 _pass。

tests/riscv/riscv-macros.h · 第 33–44、69–72、111–114 行
#define TEST_RISCV_END          \
_pass:                          \
    addi   x29, x0, 1;          \
                                \
_fail:                          \
    li     x2,  1;              \
    csrw   21, x29;             \
1:  bne    x0, x2, 1b;          \
    nop; nop; ... （40 個 nop）

#define TEST_CHECK_EQ( reg_, value_ )   \
    li    x29, __LINE__;                \
    li    x1, value_;                   \
    bne   reg_, x1, _fail;              \

#define TEST_IMM_OP( inst_, src0_, imm_, result_ )  \
    li    x2, src0_;                                \
    inst_ x4, x2, imm_;                             \
    TEST_CHECK_EQ( x4, result_ );                   \

注意 _pass 後面沒有跳轉——它直接「掉進」_fail。這是故意的：兩條路只差在 x29 的值，共用同一段回報程式碼。最後那四十個 nop 是保險，讓 csrw 有足夠時間走完管線；就算你的 bne 還沒實作、自我迴圈跳不動，csrw 也已經寫進去了，測試還是會有結果。

驗算一下

看到 *** FAILED *** (status = 137) 怎麼辦

137 就是 __LINE__。打開對應的 .S 檔跳到第 137 行，那一行的巨集就是失敗的檢查——它會告訴你是哪一條指令、哪一組輸入、期望什麼結果。status = 2 是例外：benchmark 的 test_fail 固定寫 2，沒有行號。

想一想

某位同學的 bne 控制列寫錯了，br_sel 填成 br_none，導致所有 bne 都不跳。跑 riscv-addi 會看到什麼？

看答案

*** PASSED ***——而且是假的。因為所有檢查的 bne ..., _fail 都不跳，程式一路直直走到 _pass，x29 被設成 1。這正是為什麼一定要跑 riscv-bne：它裡面的 TEST_BR2_OP_TAKEN 會在「該跳卻沒跳」時落到 TEST_CHECK_FAIL，強制失敗。單一測試通過不代表指令對了。

+vcd=1 產生的檔名是「+exe= 的路徑去掉最後 3 個字元再接 .vcd」，所以每次跑同一個測試都會蓋掉上一次的波形。要留下來就先改名。另外 make check-asm-* 預設 VCD=0；要整批產生波形得下 make check-asm-riscvstall VCD=1。

加一個自己的測試

講義第 4 節要求你至少為 mulh / mulhu / mulhsu 寫測試，外加一個針對你遇過的 bug 的測試。整個流程只有四步，但四步都漏不得——漏了第 1 步檔案不會被編譯，漏了第 3 步 make 會說找不到 .vmh。

寫測試時請直接模仿 riscv-mul.S：TEST_RR_OP( mulh, 被乘數, 乘數, 期望的高 32 位元 )，然後補上 SRC0_EQ_DEST、SRCS_EQ_DEST 這幾個邊界情況，最後加上 *_BYP 系列（第 16 章詳細解釋過 nops_ 參數怎麼對應到三條 bypass 路徑）。有號數的高位元最容易錯，記得測 0x80000000 × 0x80000000 這種兩個都是負數、以及 mulhsu 一有號一無號的組合。

Benchmark：把 C 程式塞進一顆沒有作業系統的 CPU

ubmark/ 裡的四個程式是真正的 C。它們能在這顆 CPU 上跑，靠的是三個「作弊」：

  • 沒有 main 的啟動流程：用 -nostartfiles -nostdlib 編譯，linker script test.ld 把程式放在 0x80000，CPU reset 後直接從那裡開始。
  • 沒有 printf：驗算結果是程式自己比對陣列，然後用跟組語測試一模一樣的手段回報。
  • 輸入資料寫死在原始碼裡：#include "ubmark-vvadd.dat" 是一個產生好的陣列，變成 .data 段，跟著 .vmh 一起被 $readmemh 載進記憶體。
常見錯誤

test_stats_on 寫的是 CSR 10，而 CoreCtrl 的 case 只認 12'd21，所以這一對 csrw 在 lab1 裡沒有作用。Pattern.v 的 num_cycles 是從 reset 數到結束的整段週期數，不是只數核心迴圈。比較三個版本的效能時這沒問題（大家都用同一把尺），但別把它當成「vvadd 迴圈本身的週期數」。

評估時要比較的就是 .out 裡的 num_cycles 與 ipc。num_inst 三個版本應該幾乎一樣（同一個程式、同樣多的指令退休），會變的是 num_cycles：

版本期望的變化為什麼
riscvstall基準每個資料冒險都要 stall 到寫入者離開 W
riscvbypnum_cycles 明顯下降、ipc 上升大部分冒險改用旁路，只剩 load-use 要 stall 一拍（第 14 章）
riscvlong有乘除法的 benchmark 再降一截管線化的乘法器不再讓 X 卡住整條管線（第 18 章）
做實驗的紀律

make check-asm-* 與 run-bmark-* 會覆蓋同名的 .out 與 .vcd。要做三個版本的比較，跑完一個就把 .out 收到別的目錄去（或用 cp *-stall.out results/），不然最後一輪會把前面的結果洗掉。

第 21 章 · 測試與除錯

除錯方法與速查表

最後一章不教新電路，教怎麼把「它壞了」變成「它在第 N 個週期、因為 X 訊號、所以壞了」。管線 CPU 的好處是：錯誤的種類其實很少，而且每一種都有固定的症狀。

症狀 → 嫌疑犯

逐一展開：

① 滿畫面的 x assertion failed，最後 timeout

這是「控制表沒有這一列」的真實症狀（用 riscv-lh.vmh 在還沒加 lh 的 riscvstall 上實測）：

實測輸出：vvp ./riscvstall-sim +exe=riscv-lh.vmh
 RTL-ERROR ( time = 125 ) Testbench.pattern.mem.mem : x assertion failed : memresp1_rdy
 RTL-ERROR ( time = 125 ) Testbench.pattern.mem.mem : x assertion failed : memreq1_val
 RTL-ERROR ( time = 125 ) Testbench.pattern.mem.mem : x assertion failed : memresp0_rdy
 RTL-ERROR ( time = 125 ) Testbench.pattern.mem.mem : x assertion failed : memreq0_val
 ...（同樣四行每個週期重複，約四十萬行）
*** FAILED *** (timeout)

原因：casez 開頭把 cs 預設成全 x，沒有任何一列命中時，這道指令的每一個控制欄位都是 x——包含 MEM_REQ、MULDIV_EN、J_EN 這些致能。x 流進 stall_Dhl、dmemreq_val、imemreq_val，測試記憶體發現它的 val／rdy 腳是 x 就開始報錯；管線的 stall 也變成 x，PC 不再前進，最後 timeout。第一行錯誤的時間就是那道指令進到 D 級的時間，在波形上看那一刻的 ir_Dhl 就知道是誰。

不要等 Illegal instruction!

CoreCtrl 結尾（第 875–889 行）確實有一段 assertion 會印 RTL-ERROR : Illegal instruction!，條件是 !cs[`RISCV_INST_MSG_INST_VAL]。但沒命中時 cs[38] 是 x，!x 還是 x，而 if (x) 在模擬裡不成立——所以缺一列時這句話不會出現。只有當某一列明確把 val 欄填成 n 時它才會觸發。

三個最常見的原因，照順序檢查：控制表那一列還被註解著；InstMsg.v 裡對應的 `define 還被註解著（Objective 2 的 mulh 系列就是這樣）；或者 casez 的樣式打錯，讓某個 ? 變成 0。想確認是哪一條指令，在波形裡看那個週期的 ir_Dhl，對照 riscv-isa.txt 解碼。

② FAILED (status = N)：縮小到某個控制欄位

指令有被解碼（不然會是 ①），但做出來的事情不對。控制表有 19 個欄位，但對一條指令來說可疑的通常只有三、四個。用「這條指令要用到誰」來篩：

如果結果…先看這些欄位
數值算錯，但來源暫存器沒問題alu_fn、op1_sel（立即數型別對不對）
結果跟某個輸入一模一樣op0_sel / op1_sel 選錯來源
目標暫存器根本沒被寫rf_wen、rf_waddr
讀到舊值（該 stall 卻沒 stall）rs1_en / rs2_en（第 11 章）
load/store 的位元組數不對mem_len、memresp_sel
分支該跳不跳 / 不該跳卻跳br_sel、alu_fn、以及 any_br_taken_Xhl 有沒有加上新的 *_taken_Xhl
常見錯誤：新分支忘了接進 any_br_taken_Xhl

控制表填了 br_beq、也宣告了 beq_taken_Xhl，但沒把它 or 進 any_br_taken_Xhl。症狀是分支永遠不跳——而且 riscv-addi 之類的測試反而「通過」（見上一章的想一想）。

③ timeout

三種可能，分辨方法是看 pc_Fhl：

  • pc_Fhl 每個週期都在變、但跑到奇怪的位址：跳轉目標算錯。看 pc_mux_sel_Phl 與 branch_targ / jump_targ / jumpreg_targ，通常是 pc_sel 欄位或立即數型別填錯。
  • pc_Fhl 完全不動：死結。某條 stall_* 永遠是 1。最典型的是 stall 條件忘了用 inst_val_* 把 bubble 濾掉——bubble 的 rf_waddr_Xhl 是殘留值，會跟 D 的 rs1 無限撞上。另一種是 val/rdy 沒處理好：請求已經被對方收走了卻還一直送，或者 rdy 的條件寫成需要對方先給 val（互等）。
  • PC 停在 _fail 那個自我迴圈：程式其實跑完了，但 csrw 沒生效。看 W 階段的 csr_wen_Whl 與 inst_val_Whl 是不是曾經同時為 1。

④ 只有 -rand- 失敗

固定 1 週期的記憶體會掩蓋掉所有「多等幾拍」的 bug。第 13 章講過 stall_dmem_Xhl（請求送不出去）與 stall_dmem_Mhl（回應還沒來）這一對；只要少了一個，快的記憶體看不出來，慢的記憶體馬上炸。順便：dmemreq_val 的條件是 inst_val_Xhl && !stall_Xhl && dmemreq_val_Xhl，三個缺一不可。

⑤ 波形裡一片 x

控制表裡的 alu_x、ml_x、dmm_x 是真的 1'bx。填 x 的前提是「這條指令真的不會用到那個欄位」。如果某條線被填了 x 卻還是被下游消費（例如 rf_waddr 填 rx，但 rf_wen 卻是 y），x 會沿著管線擴散，最後整個暫存器檔變成 x。除錯法：從最早變成 x 的那條線往上游找。

讀逐週期的管線追蹤

riscvstall/riscvstall-sim.v 第 199–270 行有一段很好用的列印：每個 posedge 印一行，五個欄位對應五個階段。目前 build/Makefile 編的是 Testbench.v + Pattern.v 這條路徑，並沒有把 -sim.v 編進去（它還引用了已經不存在的 proc.ctrl.stats_en），不過那段 $write 可以整段搬到 Pattern.v 裡用，路徑改成 Testbench.proc.ctrl.… 即可。它的編碼規則值得背起來：

if ( proc.ctrl.bubble_Dhl )
  $write( "  (-_-) " );
else if ( proc.ctrl.squash_Dhl )

+disasm 的三個層級

+disasm=1 每退休一條指令印一行 PC: 機器碼: 反組譯；+disasm=2 再加印整個暫存器檔；+disasm=3 才是上面那種逐週期五階段追蹤。搬進 Pattern.v 時記得也把這個 plusarg 一起搬。

gtkwave：先加哪些訊號

build/template.sav 是一個現成的 gtkwave save 檔，訊號順序就是按「指令在管線裡走的順序」排的：PC 計算 → imem → D 解碼與讀暫存器 → 運算元 mux → ALU 與分支條件 → dmem → 寫回 mux → rf_wen / rf_waddr → inst_val / squash / stall / bubble 四組控制旗標。

用 template.sav 前要改一行

裡面的路徑全部以 riscv_sim. 開頭（舊的獨立模擬器的頂層名）。現在的波形頂層是 Testbench，所以要先轉換：sed 's/riscv_sim\./Testbench./g' template.sav > my.sav，再 gtkwave riscv-addi.vcd my.sav。另外它列了 op0_byp_mux_sel_* 與 stall_load_use_*，這兩個在 riscvstall 還不存在（是你在 Objective 3 才會加的），gtkwave 會顯示為找不到，屬正常。

如果從零開始加，這個順序最省時間：

順位訊號回答什麼問題

從錯的寫入往回走

最有效率的除錯法不是從頭順著看，而是從結果錯的那一刻往回推。暫存器檔只有一個寫入埠，所以「某個暫存器的值不對」一定對應到 W 階段的某一拍。

想一想

波形上看到 W 階段 rf_waddr_Whl = 0、rf_wen_out_Whl = 1，但你期望寫的是 x4。這算 bug 嗎？

看答案

寫進 x0 本身無害（x0 硬體固定為 0，寫不進去），但它說明 rf_waddr 欄位填成了 r0 或 rx——真正的 bug 是「x4 從來沒被寫過」。而且這個錯誤在 riscvstall 還會連帶讓 stall_hazard_Dhl 判斷錯：它比對的就是 rf_waddr_*，位址錯了，該 stall 的地方也不會 stall。

下一步

把四個 Objective 按順序走一遍，每一步都用上一章的測試方法確認完才往下：

  1. Objective 1：補完控制表（第 8 章的食譜）。從 addi 這類最像現有列的指令開始，每加一條就跑它自己的測試。分支與 load/store 留到最後，因為它們還要動 any_br_taken_Xhl 和 subword 欄位。
  2. Objective 2：mulh / mulhu / mulhsu（第 17 章）。先把 InstMsg.v 的 `define 取消註解，再補控制列，然後才動 imuldiv。測試要自己寫——這是講義明文要求的。
  3. Objective 3：bypass（第 14–16 章）。改 riscvbyp，先只做 X→D 一條路徑跑通，再加 M→D、W→D，最後處理 load-use 的那一拍 stall。每加一條路徑就跑一次 *_BYP 測試。
  4. Objective 4：管線化乘除法（第 18–19 章）。改 riscvlong，完成後用 benchmark 的 num_cycles 證明它真的變快了。

每完成一個 Objective，記得回到 build/Makefile 把對應的 subpkgs、sim_incs、proc_template、asm_template、bmark_template 五處註解取消，新版本才會被編譯與測試。
