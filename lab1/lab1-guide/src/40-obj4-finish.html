第 9 站 · Objective 4（30%）

riscvlong：接上管線化乘除法器

這一站的分數最重（30%），風險也最高：它不是「加一個功能」，而是把整條管線從 5 級改成 7 級， 然後把原本會讓全機停 30 幾拍的迭代式乘除法器，換成一個固定 4 級延遲、每拍都能收新請求的管線化單元。 牽動的檔案是 riscvlong-CoreCtrl.v、riscvlong-CoreDpath.v、riscvlong-Core.v、 riscvlong-CoreDpathPipeMulDiv.v 四支。

理論在圖解課已經講完了，這一站只講做事的順序。開工前請先把 圖解課第 19 章讀過一遍（7 級管線長什麼樣、mul-use 是什麼）， 必要時回頭看 第 17 章（乘除法器今天怎麼掛在 X 級）。

一句話策略

不要一口氣改完。把它拆成六個里程碑，每一個都有一條可以跑的測試指令當關卡。 其中 M1（只延長管線、完全不碰乘除法器）是整站最重要的一步：它讓你把「管線延長的 bug」和「乘除法整合的 bug」分開來除錯。 跳過 M1 直接全改，是這個作業最常見的翻車方式。

M0：前置條件與開工

Objective 4 是接在 Objective 3 後面的：riscvlong/setup.sh 是從 ../riscvbyp/ 用 rsync 整包複製過來的 （跟 第 7 站說明的 riscvbyp/setup.sh 同一套機制，只是來源換成 riscvbyp）。 所以 riscvbyp 有多完整，riscvlong 就從多完整的地方起跑。

  1. 先確認 riscvbyp 是乾淨的

    全部 assembly 測試（含 rand 版）都要 PASSED。riscvbyp 裡殘留的旁路 bug 會被複製到 riscvlong， 然後你會在一個 7 級管線裡追一個其實是 5 級管線就有的錯。

    % cd $LAB1_ROOT/build
% make check-asm-riscvbyp
% make check-asm-rand-riscvbyp
  2. 跑 setup.sh

    它會把 ../riscvbyp/ 的所有檔案（除了 setup.sh 本身）複製過來、把檔名的 riscvbyp 前綴改成 riscvlong、再 sed 掉檔案內容裡的字串。riscvbyp-CoreDpathPipeMulDiv.v 也會一路跟著變成 riscvlong-CoreDpathPipeMulDiv.v（模組名 riscv_CoreDpathPipeMulDiv 不變）。

    % cd $LAB1_ROOT/riscvlong
% ./setup.sh
% ls
  3. 打開 build/Makefile 的 riscvlong 五處

    跟 riscvbyp 一模一樣的五個位置，都標著 # Enable these after running their setup.sh scripts.： subpkgs +=（第 73 行）、sim_incs += -I（第 118 行）、proc_template（第 179 行）、 asm_template（第 218 行）、bmark_template（第 261 行）。 每一行只要把開頭的 # 拿掉。做法與注意事項見 第 7 站。

  4. 先跑一次基準線

    此時 riscvlong 只是 riscvbyp 的複本，所有測試應該直接全過。 這一次執行的意義是確認「五處註解都解對了、模擬器建得起來」，而不是驗證任何新功能。

    % cd $LAB1_ROOT/build
% make check-asm-riscvlong
常見錯誤

做到一半發現 riscvbyp 有 bug，於是回頭改 riscvbyp 再重跑一次 riscvlong/setup.sh —— 這會把你在 riscvlong 做的所有工作整包蓋掉。setup.sh 只能跑一次。之後 riscvbyp 的修正必須手動同步到 riscvlong。

M1：先把管線延長，乘除法器一個字都不要改

手冊建議的做法是：乘除法單元的第 0、1 級疊在現有的 X、M 上（免費，不增加延遲）， 第 2、3 級沒有現成的級可以疊，所以真的新增兩個管線級 X2、X3，插在 M 和 W 之間。

M1 的工作就是把 X2、X3 這兩個空殼級做出來，什麼功能都不加。做法是照抄： riscvlong-CoreCtrl.v 裡的 // M <- X 區段（riscvstall 版在第 693–723 行）是最好的模板， 整段複製兩次，字尾改成 _X2hl、_X3hl，最後把 W <- M 改成 W <- X3。

riscvstall/riscvstall-CoreCtrl.v · 第 695–723 行（節錄，當作模板）
  reg [31:0] ir_Mhl;
  reg        dmemreq_val_Mhl;
  reg        rf_wen_Mhl;
  reg  [4:0] rf_waddr_Mhl;
  reg        csr_wen_Mhl;
  reg [11:0] csr_addr_Mhl;

  reg        bubble_Mhl;

  always @ ( posedge clk ) begin
    if ( reset ) begin
      bubble_Mhl <= 1'b1;
    end
    else if( !stall_Mhl ) begin
      ir_Mhl               <= ir_Xhl;
      dmemresp_mux_sel_Mhl <= dmemresp_mux_sel_Xhl;
      wb_mux_sel_Mhl       <= wb_mux_sel_Xhl;
      rf_wen_Mhl           <= rf_wen_Xhl;
      rf_waddr_Mhl         <= rf_waddr_Xhl;
      csr_wen_Mhl          <= csr_wen_Xhl;
      csr_addr_Mhl         <= csr_addr_Xhl;

      bubble_Mhl           <= bubble_next_Xhl;
    end
    dmemreq_val_Mhl <= dmemreq_val;
  end

資料面同理：riscvlong-CoreDpath.v 的 pc_Mhl / wb_mux_out_Mhl （riscvstall 版在第 297–305、340–342 行）也要各補兩份。每新增一級，下面三類東西各要一份：

類別要補什麼漏掉的症狀
控制暫存器
CoreCtrl		ir_、rf_wen_、rf_waddr_、csr_wen_、csr_addr_、wb_mux_sel_、bubble_寫錯暫存器、或 CSR 的 PASS 寫入提早／永遠不發生
資料暫存器
CoreDpath		pc_、寫回資料（M 級選完的 wb_mux_out_）寫回值錯一級，或 disasm 顯示的 pc 對不上
每級三條線
CoreCtrl		inst_val_（!bubble && !squash）、squash_（先接 1'b0）、stall_（往前串）bubble 被當成真指令寫進暫存器檔，程式跑到一半暫存器莫名被改

stall 鏈的方向千萬別接反。7 級之後它是：

stall_Whl(0) → stall_X3hl → stall_X2hl → stall_Mhl → stall_Xhl → stall_Dhl → stall_Fhl
M1 的驗收標準很明確

改完之後所有測試仍然全部 PASSED，只是 num_cycles 比 riscvbyp 多幾拍（排乾管線多兩拍）。 如果有任何一支從 PASSED 變 FAILED，那就是純粹的管線延長 bug，跟乘除法器無關 —— 現在修最便宜。

M2：旁路來源從 3 個變 5 個

在 riscvbyp 裡，D 級的旁路多工器有 X、M、W 三個來源。管線變長之後， 一個還沒寫回的值可能停在 X、M、X2、X3、W 五個地方的任何一個 —— 少接一個，那個相依就會讀到舊值。

示意範例（形狀，不是答案）
  wire rs1_X2_byp_Dhl = rs1_en_Dhl
                     && inst_val_X2hl
                     && rf_wen_X2hl
                     && ( ... == rf_waddr_X2hl )
                     && ( rf_waddr_X2hl != 5'd0 );
  // rs2 / X3 各再一份；選擇訊號的優先權由新到舊排列
  wire [2:0] op0_byp_mux_sel_Dhl
    = ( rs1_X_byp_Dhl  ) ? ...
    : ( rs1_M_byp_Dhl  ) ? ...
    : ( ... )            ? ...   // X2、X3、W 依序
    :                      ...;

load-use 規則也要跟著調整。載入值在 M 級末端才到手，這點 7 級和 5 級一樣 —— 所以 load-use 仍然只停 1 拍。但你必須確認：當 load 走到 X2、X3 時，消費者是走「旁路」而不是「stall」， 否則會多停兩拍，benchmark 數字會莫名其妙變差。

M3：換上管線化乘除法單元

三件事：換 `include、換例化、把運算元改從 D 級取。

riscvstall/riscvstall-CoreDpath.v · 第 426–438 行（今天的接法）
  imuldiv_IntMulDivIterative imuldiv
  (
    .clk                   (clk),
    .reset                 (reset),
    .muldivreq_msg_fn      (muldivreq_msg_fn_Xhl),
    .muldivreq_msg_a       (op0_mux_out_Xhl),
    .muldivreq_msg_b       (op1_mux_out_Xhl),
    .muldivreq_val         (muldivreq_val),
    .muldivreq_rdy         (muldivreq_rdy),
    .muldivresp_msg_result (muldivresp_msg_result_Xhl),
    .muldivresp_val        (muldivresp_val),
    .muldivresp_rdy        (muldivresp_rdy)

手冊用粗體寫了一句：「Ensure the muldiv unit receives values immediately after the D (Decode) stage instead of the X (Execute) stage.」這不是建議，是必要條件。

riscvstall/riscvstall-CoreDpathPipeMulDiv.v · 第 24–34 行
  //These need to be hooked up to something!
  input         stall_Xhl,
  input         stall_Mhl,
  input         stall_X2hl,
  input         stall_X3hl
);

  // Set request ready if not stalled

  assign muldivreq_rdy = !stall;
  wire   muldivreq_go  = muldivreq_val && muldivreq_rdy;

單元內部用三組不同的致能：輸入級跟 stall_Xhl 走、result1_reg 跟 stall_Mhl 走、 後兩級目前跟單元自己的 stall 走（第 74–86 行）。stall_X2hl 和 stall_X3hl 兩個埠在模組裡 完全沒有被使用 —— 那是留給你的功課：處理器延長成 7 級之後，後兩級應該跟著新的 X2、X3 一起停。

M4：結果在哪裡併回來，以及 mul-use 冒險

乘除法結果在 result3_reg（X3 這一拍）才存在，然後在 W 之前併進寫回多工器。 由此產生一個新的冒險：mul-use。

舊的 stall 要拆掉，但要想清楚再拆。riscvstall / riscvbyp 裡有兩條專為迭代式單元存在的 stall：

riscvstall/riscvstall-CoreCtrl.v · 第 553、675 行
  wire stall_muldiv_Dhl = ( muldivreq_val_Dhl && inst_val_Dhl && !muldivreq_rdy );
  ...
  wire stall_muldiv_Xhl = ( muldivreq_val_Xhl && inst_val_Xhl && !muldivresp_val );
  • stall_muldiv_Xhl（等 muldivresp_val）必須拆掉。管線化單元的回應要到 X3 才來， 如果 X 級還在等它，整個 Objective 的意義就沒了 —— 效能會跟 riscvbyp 一樣爛甚至更爛。
  • stall_muldiv_Dhl（等 muldivreq_rdy）不要無腦拆掉。管線化單元的 muldivreq_rdy = !stall，而 stall = val3_reg && !muldivresp_rdy（第 161 行）—— 也就是「結果卡在出口沒人收」時它還是會拒收新請求。這條反壓仍然需要被尊重，只是觸發的條件變罕見了。
  • muldivresp_rdy 原本是 !stall_Xhl（第 650 行），現在收回應的是 X3 那一端， 要跟著改成對應的級。

M5：把 mulh 家族補進 PipeMulDiv

你在 Objective 2 是改 imuldiv-IntMulIterative.v / imuldiv-IntMulDivIterative.v（見 第 6 站）。 那些修改不會自動出現在管線化單元裡 —— riscv_CoreDpathPipeMulDiv 是另一份獨立實作， 它的 result0 今天只認得五個 function：

riscvstall/riscvstall-CoreDpathPipeMulDiv.v · 第 138–144 行
  wire [63:0] result0
    = ( fn_reg == `IMULDIV_MULDIVREQ_MSG_FUNC_MUL  ) ? product
    : ( fn_reg == `IMULDIV_MULDIVREQ_MSG_FUNC_DIV  ) ? { remainder, quotient }
    : ( fn_reg == `IMULDIV_MULDIVREQ_MSG_FUNC_DIVU ) ? { remainderu, quotientu }
    : ( fn_reg == `IMULDIV_MULDIVREQ_MSG_FUNC_REM  ) ? { remainder, quotient }
    : ( fn_reg == `IMULDIV_MULDIVREQ_MSG_FUNC_REMU ) ? { remainderu, quotientu }
    :                                                  32'bx;

你在 Objective 2 為 mulh / mulhu / mulhsu 定義的三個新 function 編碼落到這裡會變成 32'bx，於是 riscv-mulh-long.out 直接 FAILED。 riscvlong-CoreDpathPipeMulDiv.v 本來就在手冊第 6.1 節的修改檔案清單裡 —— 它預期你會改它。

要做的事：在這個 result0 鏈上補三條分支，各自產生正確的 64 位元乘積上半。 單元裡已經有 a_unsign / b_unsign / sign / product_raw / product 這些現成的中間值（第 98–122 行），三種有號性組合要怎麼從它們兜出來，在 Objective 2 你已經推過一次， 邏輯完全相同，只是換個地方寫。

常見錯誤

只改了 result0，忘記 muldiv_mux_sel（選 64 位元結果的高半／低半）在 riscvlong 的控制表裡 也要對 mulh 家族設成「取高半」。這兩處要一起對，才會拿到對的 32 位元。

M6：回歸與收尾

  1. 三個處理器一起跑

    riscvlong 的工作不應該動到 riscvstall 或 riscvbyp。如果它們壞了，代表你改錯目錄了。

    % cd $LAB1_ROOT/build
% make check-asm-riscvstall
% make check-asm-riscvbyp
% make check-asm-riscvlong
  2. 隨機延遲版

    -rand 版會在記憶體回應上加隨機延遲，最容易抓出「stall 期間某個暫存器該保持卻被更新」這類 bug。

    % make check-asm-rand-riscvlong
  3. benchmark

    見 第 10 站。benchmark 全過是最強的正確性證據。

    % make run-bmark-riscvlong
這一站的陷阱清單

(1) 漏掉 csr_wen 的複製。測試靠 csrw 21, x29 回報 PASS/FAIL。X2、X3 忘了接 csr_wen / csr_addr，那筆寫入就永遠不會發生（測試 timeout），或早兩拍發生（讀到還沒算好的值）。
(2) rf_waddr 比對用錯級。寫 rs1_X3_byp_Dhl 時整段複製貼上，裡面卻還留著 rf_waddr_X2hl。症狀是特定距離的相依才錯，非常難抓 —— 寫完後把每個 byp 訊號的級字尾逐字念一遍。
(3) stall 鏈順序接反。正確方向是 stall_Whl(0) → stall_X3hl → stall_X2hl → stall_Mhl → stall_Xhl → stall_Dhl → stall_Fhl。 接反了會出現「前面停、後面繼續跑」，指令被複製或吃掉。
(4) 四條 stall 線沒接完。stall_X2hl / stall_X3hl 留空，單元內部的 val0..val3 就會和核心的 bubble 位元失去同步：核心停了，單元卻繼續往前推，結果在一個沒人要的拍數出現。
(5) Verilog 隱含 1-bit net。打錯字的 stall_X2h1（數字 1）不會報錯，會自動變成一條 1-bit wire。 除錯時可以暫時在檔案最上面加 `default_nettype none 讓這類錯誤變成編譯錯誤， 也一定要看 iverilog -Wall 的警告輸出 —— 但記得繳交前拿掉，以免影響其他檔案。

第 10 站 · 收尾

Benchmark 評估

手冊第 5 節要求用 $LAB1_ROOT/ubmark 下的四支 C benchmark 評估三個處理器。 評分是 100% 看程式碼，沒有報告分數 —— 但 benchmark 是最強的正確性證據： 它們是真實的 C 程式，會用到 assembly 測試不見得涵蓋的指令組合與相依距離。 assembly 測試全過但 benchmark 掛掉，幾乎一定是你的旁路或 stall 有洞。

先把 benchmark 編出來

build/Makefile 的 bmarks =（第 56–60 行）列了四個 .vmh，但 build/Makefile 裡沒有編它們的規則 （assembly 測試有，benchmark 沒有）。它靠 VPATH += $(topdir)/ubmark/build/vmh（第 82 行）去找現成的檔案。 所以你必須先在 ubmark/ 自己 configure + make 一次。

  1. 在 ubmark 下建一個 build 目錄並 configure

    ubmark/ 裡有 configure、Makefile.in、 convert、以及 ubmark/ubmark/ 放四支 .c 和它們的 .dat 測資。 和 tests/ 完全一樣的 autoconf 流程。

    % cd $LAB1_ROOT/ubmark
% mkdir build
% cd build
% ../configure --host=riscv32-unknown-elf
% make
  2. 跑 convert

    它會建出 bin/ dump/ vmh/ obj/ dep/ 五個子目錄，把 ELF 搬進 bin/， 對每個執行檔跑一次 objdump，再用 scripts/objdump2vmh.py 轉成 .vmh。

    % ../convert
% ls vmh

    跑完應該看到四個檔：ubmark-vvadd.vmh、ubmark-cmplx-mult.vmh、 ubmark-masked-filter.vmh、ubmark-bin-search.vmh。

  3. 回 build 跑

    run-bmark-* 會用 BMARK_SIM_FLAGS = +verbose=1 （build/Makefile 第 127 行）執行，所以 .out 裡會有 STATS 區塊。

    % cd $LAB1_ROOT/build
% make run-bmark-riscvstall
% make run-bmark-riscvbyp
% make run-bmark-riscvlong
benchmark 在 Objective 1 完成之前一定跑不過

四支 C 程式會用到 slli、sub、beq、lbu 等 還沒加進控制表的指令。控制表沒有那一列 → cs 整包是 x → 訊號變 x， 你會看到滿螢幕的 RTL-ERROR ... x assertion failed : memreq0_val，最後 *** FAILED *** (timeout)。這不是 benchmark 壞掉，是 Objective 1 還沒做完。先把 check-asm 全部弄綠再來跑 benchmark。

四支 benchmark 各操什麼

benchmark主要運算會不會用到乘法器掛掉時先懷疑
ubmark-vvadd向量逐元素相加，單純迴圈核心迴圈沒有乘法基本的 load / store / add / 分支、load-use
ubmark-cmplx-mult複數乘法：每個元素 4 次乘法 + 加減大量 mulmul 的控制表列、mul-use stall、乘除法器整合
ubmark-masked-filter5 點遮罩濾波：乘係數後除以 norm乘 + 除（out/norm 是變數除法）mul、divu、位元組載入 lbu、型別轉換
ubmark-bin-search二分搜尋，大量比較與分支只有 /2（編譯器會轉成移位）各種分支 beq/bge/bltu、slt 家族、control hazard

把數字填進這張表

數字從 .out 檔尾的 STATS 區塊讀。格式和 assembly 測試一樣，例如 riscv-add-stall.out：

*** PASSED ***
--------------------------------------------
 STATS
--------------------------------------------
 status     =          1
 num_cycles =        468
 num_inst   =        232
 ipc        = 0.495726
常見錯誤

只跑 make run-bmark-riscvlong 就下結論。要比較就得三個都跑，而且 在同一份 ubmark/build/vmh 上跑。中途重編 benchmark（改了 .c 或換了 gcc 版本）會讓 num_inst 變動，前後的數字就不能比了。

macOS 專屬的三個坑

(1) .DS_Store 與 ._*。Finder 逛過的目錄都會留下 .DS_Store； macOS 內建的 tar 預設還會為每個檔案額外塞一個 ._檔名 的 AppleDouble 附檔。 解開之後助教會看到一堆 ._riscvlong-CoreCtrl.v，很醜而且可能干擾自動化腳本。 用 COPYFILE_DISABLE=1 關掉 AppleDouble，用 --exclude .DS_Store 排掉前者。
(2) .git 目錄。你的工作目錄裡有 .git。它可能比全部原始碼加起來還大好幾倍， 而且含有你的 commit 訊息與 email。手冊只要求原始碼，建議用 --exclude .git 排掉。 （若你的 .git 在外層而不是內層 lab1/ 裡，就不會被打包進去，加這個參數也無害。）
(3) rm -rf 打在錯的目錄。cd $LAB1_ROOT/tests 和 rm -rf build 是兩行； 如果第一行因為打錯字沒成功，第二行就會在你原本所在的目錄執行。 安全的寫法是把它們寫成一行：rm -rf $LAB1_ROOT/tests/build $LAB1_ROOT/ubmark/build， 路徑寫死，不依賴當下位置。

像助教一樣驗收你的 tarball

交出去之前，用一個全新的空目錄把它解開再重建一次。這會抓到所有「只有在我的機器上才會過」的問題： 忘了 commit 的檔案、被 clean 掉卻沒有重建規則的產生物、寫死的絕對路徑。
