第 6 站 · Objective 2（15%）

Objective 2：mulh / mulhu / mulhsu

這一站要在 riscvstall 上補完 RV32M 的三條「取乘積高半」指令。和 第 5 站不一樣的地方在於：前面那 32 條指令，硬體本來就做得到，你只是在控制表上填格子；這三條裡有兩條（mulhu、mulhsu）現有的乘法器算不出來，你得動到 imuldiv/ 裡面。所以它只佔 15%，卻是整個 Lab 1 裡唯一一處要你改運算單元的地方。

開工前先把圖解課第 17 章（乘除法器怎麼掛在管線上）和第 18 章（mulh 家族）看過——那兩章把「為什麼低半不分有號無號、高半要分」和「現有乘法器的符號包覆層」講完了。這一站只講你要動的檔案、動的順序、和怎麼確認動對了。

三條指令，兩種難度

先把工作量估對，才不會把三條指令當成一樣的事：

指令要動 imuldiv/ 嗎做什麼
mulh不用送給單元的仍是 md_mul，只是控制表的 MULDIV_SEL 欄填 mdm_u（取高半）。純粹是 InstMsg 一個 define ＋ CoreCtrl 一列。
mulhu要兩個運算元都當無號：不取絕對值、結果不取二補數。
mulhsu要a 有號、b 無號：只有 a 取絕對值，結果符號只看 a[31]。
順序建議

先只做 mulh，跑一次測試看到 PASSED，再回頭動乘法器。這樣「控制表填錯」和「乘法器改壞」這兩類錯誤不會混在一起——不然你看到 FAILED 會完全不知道要往哪邊查。

改動會穿過五個檔案

這三條指令的資訊會沿著一條線傳下去：指令位元 → 控制表解出 muldivreq_msg_fn_Dhl → 管線化成 muldivreq_msg_fn_Xhl → 進 imuldiv_IntMulDivIterative 分流 → 進乘法器決定符號怎麼處理。這條線上每一段都要你補一塊，少一塊，訊號就在那裡斷掉。

riscvstall/riscvstall-InstMsg.v · 第 146–149 行
`define RISCV_INST_MSG_MUL      32'b0000001_?????_?????_000_?????_0110011
// `define RISCV_INST_MSG_MULH     32'b0000001_?????_?????_001_?????_0110011  // not supported.
// `define RISCV_INST_MSG_MULHSU   32'b0000001_?????_?????_010_?????_0110011  // not supported.
// `define RISCV_INST_MSG_MULHU    32'b0000001_?????_?????_011_?????_0110011  // not supported.

編碼已經寫好了，你只要把 // 拿掉。注意順序：funct3 是 001=mulh、010=mulhsu、011=mulhu——mulhsu 排在 mulhu 前面，抄的時候很容易把兩個對調。

riscvstall/riscvstall-CoreCtrl.v · 第 314–325 行
  localparam md_x    = 3'bx;
  localparam md_mul  = 3'd0;
  localparam md_div  = 3'd1;
  localparam md_divu = 3'd2;
  localparam md_rem  = 3'd3;

  localparam mdm_l = 1'd0; // Take lower half of 64-bit result, mul/div/divu
  localparam mdm_u = 1'd1; // Take upper half of 64-bit result, rem/remu

「高半」到底是哪一半

乘除法單元永遠回一個 64 位元的 muldivresp_msg_result，控制表的 MULDIV_SEL 欄（mdm_l／mdm_u）決定把哪 32 位寫進 rd。這條取高半的路本來就存在，因為 rem／remu 要用它——所以 mulh 家族在資料路徑上什麼都不用加。

同樣的位元，三種高半

用 8 位元乘 8 位元（結果 16 位元）就能把三條指令的差別看完。取 a = 0xF1、b = 0x90，兩個位元樣式都固定不動，只改「怎麼解讀」：

乘法器現在怎麼處理正負號

迭代核心只會做無號乘法，有號是外面包一層：進去前取絕對值、出來後看符號決定要不要對整個 64 位元取二補數。你要改的就是這一層的兩個端點。

imuldiv/imuldiv-IntMulIterative.v · 第 142–154、224–231 行（節錄）
wire   sign_next = mulreq_msg_a[31] ^ mulreq_msg_b[31];

wire [31:0] unsigned_a
  = ( mulreq_msg_a[31] ) ? ~mulreq_msg_a + 1'b1
  :                         mulreq_msg_a;

wire [31:0] unsigned_b
  = ( mulreq_msg_b[31] ) ? ~mulreq_msg_b + 1'b1
  :                         mulreq_msg_b;

...

wire [63:0] signed_result_mux_out
  = ( sign_mux_sel == sign_u ) ? result_reg
  : ( sign_mux_sel == sign_s ) ? ~result_reg + 1'b1
  :                              64'bx;

assign mulresp_msg_result = signed_result_mux_out;
fn 要鎖進暫存器

sign_reg 是在請求被接受的那一拍鎖進去的，但結果要到 32 拍之後才用得到符號規則——那時 muldivreq_msg_fn 早就變成別的指令的值了。新增的 fn 輸入也要照樣鎖住。現成的範本就在隔壁：imuldiv-IntDivIterative.v 的控制器有一個 fn_reg，在 IDLE 時由 fn_en 鎖起來，後面一律用 fn_reg。

先取負、再切高半，順序不能換

~result_reg + 1'b1 是對完整 64 位元取二補數。如果你先切出 result_reg[63:32] 再取負，低半有借位時會差 1。mulh(-1, 3) 的正解是 0xFFFFFFFF；|−1|×3 = 3 的高半是 0x00000000，取負還是 0x00000000——錯得很安靜。

新 fn 會被送進除法器

imuldiv-IntMulDivIterative.v 第 32–39 行的分流寫的是「等於 FUNC_MUL 才給乘法器、否則一律給除法器」。你新加的 MULHU／MULHSU 不等於 MUL，預設就會跑進除法器，回來一個商或餘數。這兩個條件都要改，並把 muldivreq_msg_fn 接到 imul 新增的埠上。

預期值怎麼算才可信

不要用心算。三條指令的高半靠的是三種不同的解讀，心算 32 位元二補數出錯的機率接近 100%。用 Python 現算，它的整數是任意精度的，不會偷偷截斷：

% python3 -c 'a=0xFFFFFFFF; b=0x00000003; s=lambda x:x-(1<<32) if x>>31 else x; \
print("mul   %#010x"%((s(a)*s(b))&0xFFFFFFFF), \
      "mulh  %#010x"%(((s(a)*s(b))>>32)&0xFFFFFFFF), \
      "mulhu %#010x"%(((a*b)>>32)&0xFFFFFFFF), \
      "mulhsu %#010x"%(((s(a)*b)>>32)&0xFFFFFFFF))'

把 a、b 換掉就能量產。注意 >>32 對負數在 Python 是算術右移，正好就是「取 64 位元二補數的高 32 位」的定義。

哪些向量值得放

原則是「你改過的每一個條件分支，都要有一個向量會走到它」。對應到前面那三個「你要改的地方」：

類別代表值它打到什麼
零0任何符號邏輯的短路；0 × 負數 不該跑出 0xFFFFFFFF
一1最小的非零，抓「高半永遠算成 0」這類偷懶實作
全一-1 / 0xFFFFFFFF有號 −1 與無號 4294967295 的差距最大，三條指令答案全不同
最小負數0x80000000~x+1 對它等於自己——取絕對值電路的死角
最大正數0x7FFFFFFF有號無號解讀相同，用來確認你沒有把正數也弄壞
混合符號兩個都是負的唯一能讓 s×s／u×u／s×u 三者都不同的組合

巨集用哪一個：riscv-mul.S 已經示範了全部四種。基本正確性用 TEST_RR_OP( inst, src0, src1, result )；TEST_RR_SRC0_EQ_DEST 一類測來源等於目的；TEST_RR_DEST_BYP／TEST_RR_SRC01_BYP 是給 第 8 站的 bypass 用的，這一站先放著也無妨（riscvstall 有 stall，一樣會過）。

預期值請寫 16 進位

li 對 -1 和 0xFFFFFFFF 產生的位元完全一樣，來源寫哪一種都行；但預期值一律寫 16 進位，免得你在腦中做 32 位元截斷時出錯，結果花半小時debug 一個根本沒錯的硬體。

riscvlong 還會再要一次

第 9 站（Objective 4）用的是管線化的 riscvlong-CoreDpathPipeMulDiv.v，它是另一份乘除法實作，目前 result0（第 139–145 行）只認得 MUL／DIV／DIVU／REM／REMU。你在這一站加的三條指令，到那裡要再加一次。現在改 imuldiv/ 時，順手把你的符號規則寫成一兩句註解，第 9 站會省很多時間。

第 7 站 · Objective 3（20%）

Objective 3 開工：setup.sh 與 Makefile

Objective 3 要做的是 bypass（旁路／前饋），工作目錄是 riscvbyp/。打開來看，裡面只有一個 setup.sh：

% ls riscvbyp

這個腳本不會幫你寫任何 bypass 邏輯，它只做一件事：把你在 Objective 1、2 改好的 riscvstall/ 整個複製過來、改名。所以跑它的時間點非常重要——跑早了，你會在一份不完整的處理器上做 bypass。

跑 setup.sh 之前必須成立的前提

為什麼要這麼嚴

setup.sh 是單向的：它只會從 riscvstall 複製到 riscvbyp，不會再同步一次。如果你之後才發現 Objective 1 有一條指令的控制列填錯，你得在 riscvstall 和 riscvbyp 兩邊各修一次（到了 Objective 4 還有第三份 riscvlong）。而重跑 setup.sh 想「順便同步」的下場是：你已經寫好的 bypass 全部被覆蓋掉，無法復原。

setup.sh 做了什麼

for file in *; do

第 8 站 · Objective 3

Objective 3：bypass 實作路線

這一站不是「照著填格子」，是一個小型的電路設計。所以它要分成可以各自測試的里程碑：每做完一個就編譯一次、跑一次測試，確認沒有把原本會過的東西弄壞。一次改完五件事再編譯，你會拿到一堆互相糾纏的錯誤。

原理都在圖解課第 14–16 章；第 11 章是 data hazard 的基礎。這裡給的是順序、每一步改哪個檔、做完怎麼驗。

五個里程碑

里程碑改哪裡做完怎麼驗
M1 資料路徑：兩顆 bypass muxriscvbyp-CoreDpath.vselect 先固定接 regfile 那一路 → 行為不變，測試照樣全過
M2 控制訊號接通三個檔-CoreCtrl.v → -Core.v → -CoreDpath.v編譯過、沒有 z 或未接埠的警告；select 仍固定 → 測試全過
M3 算出 select（X > M > W）riscvbyp-CoreCtrl.v測試全過（此時 stall 還在，bypass 只是「順便」正確）
M4 拆掉泛用 stall，只留 load-useriscvbyp-CoreCtrl.v測試全過 且 cycle 數明顯下降
M5 用 *_BYP 巨集補測 ＋ 量 IPCtests/、比對 .outriscv-add-byp.out 的 num_cycles 遠小於 468
M1–M3 的共同特徵：不該改變任何行為

前三步都只是「多接一條路、多算一個訊號」，stall 邏輯原封不動，所以測試結果和 cycle 數應該一模一樣。這是很強的檢查點——任何一步做完測試就掛了，問題百分之百在你剛剛那一步。真正會改變行為的只有 M4。

M1：兩顆 bypass mux 要插在哪裡

插的位置是「所有讀 rf_rdata0_Dhl / rf_rdata1_Dhl 的地方之前」。這句話的重點是所有——在真實的 riscvstall-CoreDpath.v 裡，這兩條線各有不只一個下游：

riscvstall/riscvstall-CoreDpath.v · 第 196–230 行（節錄）
  wire [31:0] jumpreg_targ_pretruncate_Dhl = rf_rdata0_Dhl + imm_i_Dhl;
  assign jumpreg_targ_Dhl  = {jumpreg_targ_pretruncate_Dhl[31:1], 1'b0};

  ...

  wire [31:0] op0_mux_out_Dhl
    = ( op0_mux_sel_Dhl == 2'd0 ) ? rf_rdata0_Dhl
  ...
  wire [31:0] op1_mux_out_Dhl
    = ( op1_mux_sel_Dhl == 3'd0 ) ? rf_rdata1_Dhl
  ...
  // wdata with bypassing
  wire [31:0] wdata_Dhl = rf_rdata1_Dhl;

rf_rdata0_Dhl 有兩個下游（op0_mux_out_Dhl、jumpreg_targ_pretruncate_Dhl），rf_rdata1_Dhl 也有兩個（op1_mux_out_Dhl、wdata_Dhl）。第 229 行那句 // wdata with bypassing 註解就是留給你的記號。

漏掉 jumpreg_targ 的症狀

jalr 會跳到舊的位址。這件事不會讓 riscv-add 掛掉，只有 riscv-jalr.S 和 TEST_JALR_SRC0_BYP 會抓到；如果你 Objective 1 的 jalr 測試沒加進 tests =，這個 bug 會一路躲到 Objective 4。

M2：每個新訊號都要穿過三個檔案

Bypass mux 的 select 是控制訊號，所以它誕生在 CoreCtrl、使用在 CoreDpath，而這兩個模組之間沒有直接連線——中間隔著 riscvbyp-Core.v。少寫任一處，Verilog 不會報錯，只會給你一條永遠沒有驅動的線。

M3：select 怎麼算，優先權為什麼是 X > M > W

對每個來源級各做一個「這一級有沒有在寫我要讀的暫存器」的布林訊號，講義建議的命名是 rs1_X_byp_Dhl 這種形式。條件不是自己想的——直接抄現有 stall 邏輯的每一項：

riscvstall/riscvstall-CoreCtrl.v · 第 558–566 行（前兩項）
  wire stall_hazard_Dhl   = inst_val_Dhl && (
                            ( rs1_en_Dhl && inst_val_Xhl && rf_wen_Xhl
                              && ( rs1_addr_Dhl == rf_waddr_Xhl )
                              && ( rf_waddr_Xhl != 5'd0 ) )
                         || ( rs1_en_Dhl && inst_val_Mhl && rf_wen_Mhl
                              && ( rs1_addr_Dhl == rf_waddr_Mhl )
                              && ( rf_waddr_Mhl != 5'd0 ) )
                         ...

括號裡那一組四個條件，就是 rs1_X_byp_Dhl 該有的內容。inst_val_*（那一級不是泡泡）、rf_wen_*（那一級真的會寫）、rs1_en_Dhl（我真的要讀 rs1）、!= 5'd0（x0 永遠是 0，不能被前饋）——四個缺一不可。

示意範例
wire rs1_X_byp_Dhl = inst_val_Dhl && rs1_en_Dhl && ... ;
wire rs1_M_byp_Dhl = ... ;
wire rs1_W_byp_Dhl = ... ;

assign rs1_byp_mux_sel_Dhl
  = rs1_X_byp_Dhl ? 2'd1        // execute_mux_out_Xhl
  : ...                          // M、W，最後才是 regfile

三元運算子的鏈是由上往下評估的，所以把 X 寫在最前面，優先權就自動成立。

M4：只剩 load-use 需要 stall

這是唯一會改變行為的一步：把 stall_hazard_Dhl（第 558 行那一大坨）換成一個只針對 load 的停頓。為什麼只有 load 特殊，看時空圖最快：

做法：把「這條指令是 load」做成一個 1 bit 控制訊號，像 rf_wen_Dhl → rf_wen_Xhl 那樣管線化一級，然後用它去 gate 原本 X 那三項條件。現成的材料 CoreCtrl 裡都有：第 336 行的 localparam ld、第 520 行 cs[`RISCV_INST_MSG_MEM_REQ] 的用法、第 621–624 行那一串 X <- D 的管線化賦值。

示意範例
wire is_load_Dhl = ( cs[`RISCV_INST_MSG_MEM_REQ] == ld );
...

muldiv 的結果在 X 級也不一定能前饋

execute_mux_out_Xhl 在 X 級要等 muldivresp_val 才是正確值。好消息是你不用另外處理：既有的 stall_muldiv_Dhl（第 553 行）以及 X 級等待回應的 stall 已經讓 mul 在算完之前不會離開 X，D 也走不了。前提是你 M4 只拿掉 stall_hazard_Dhl，不要順手把 stall_Dhl 裡的其他項也刪掉。

M5：怎麼知道 bypass 真的在做事

這是最容易自我欺騙的一步：測試全過不代表 bypass 有生效。因為「一直 stall」本身就是正確行為，你即使 M4 完全沒做，所有測試（含 *_BYP 巨集）還是會 PASSED。唯一的證據是 cycle 數。

補測的部分，riscv-macros.h 已經備好整組 *_BYP 巨集，數字參數就是「相依距離」：

巨集測什麼
TEST_RR_DEST_BYP( n, … )n = 0/1/2 分別打到 X／M／W 三條路徑
TEST_RR_SRC01_BYP / SRC10_BYPrs1 和 rs2 兩顆 mux 都要獨立測到
TEST_LD_DEST_BYP( 0, … )就是 load-use：這一條逼出 M4 的 1 拍 bubble
TEST_BR2_SRC01_BYPbranch 的兩個來源（branch 在 X 解，但運算元仍在 D 讀）
TEST_JALR_SRC0_BYPjalr 的 rs1 → jumpreg_targ_Dhl 那條路

陷阱清單

這六個佔了絕大多數的 debug 時間
  • gating 抄漏：inst_val_*、rf_wen_*、!= 5'd0 三個條件只要漏一個，就會從一個泡泡、一個不寫暫存器的指令、或 x0 前饋出垃圾。原文在 CoreCtrl 第 558–576 行，逐項對照著抄。
  • 忘了 rs1_en / rs2_en：lui、jal 這類指令的 rs1／rs2 欄位根本不是暫存器編號，但仍會湊巧等於某個 rf_waddr。少了這個 gate，一接到 jumpreg_targ 就出事，而且會造成假相依白白吃掉 IPC。
  • 忘了 jalr 的 rs1：jumpreg_targ_pretruncate_Dhl（CoreDpath 第 196 行）還接著 rf_rdata0_Dhl。
  • 從 X 級的 load 前饋：那時資料還沒從記憶體回來，你會拿到 ALU 算出來的位址。這正是 is_load_Xhl 存在的理由。
  • x0：rf_waddr == 0 的寫入必須被排除，否則 add x0, ... 之後讀 x0 會讀到非零值。
  • 只改了 rs1 忘了 rs2：兩顆 mux、兩條 select、兩組 *_byp_Dhl 訊號，全部成對出現。TEST_RR_SRC10_BYP 專門抓這個。
